# FluxMem 在 M4 上的实际执行结果

已完成完整模型运行：Apple M4 / 16 GiB / macOS 26.5.1，Qwen2.5-VL-3B BF16，MPS + SDPA，FluxMem 作者源码未修改。三题 × 记忆开/关 × 三次交错重复，共 18 次正式问答，另有两次短前缀预热；所有调用完成，三题输出在两条件下始终为 D、C、D，与这三题金答案一致。这不是总体准确率评测。

本轮确实测到了压缩成本和内存下降，但**不能据此声称稳定加速**：相同 4 秒输入的无压缩生成时间从 2.32 秒变到 48.47 秒。后半程记录到系统 swap 占用约 7.68–10.85 GiB，并持续换入/换出；这是有内存压力的工作中 Mac，不是隔离性能环境。观察到压力不等于已证明每个尖峰的原因。

代码执行的是：视频前缀 → 视觉编码 → FluxMem 压缩 → 语言 prefill → decode。每个问题重建前缀；没有跨问题持久化的独立后台 writer。下表把视觉编码和压缩分开，不能只把压缩时间叫作全部记忆维护成本。

| 前缀 / 采样帧 | 视觉编码（秒） | 记忆压缩（秒） | 语言计算及生成余项（秒） | 完整 generate（秒；范围） |
|---|---:|---:|---:|---:|
| 4 秒 / 4 帧 | 6.58 | 0.021 | 1.37 | 8.01；2.29–10.61 |
| 53 秒 / 52 帧 | 18.78 | 1.129 | 7.75 | 27.22；25.10–81.55 |
| 82 秒 / 82 帧 | 30.86 | 2.173 | 27.63 | 59.54；45.95–108.02 |

均为同一题三次重复的中位数；各列分别取中位数，不能横向相加。语言余项包含语言 prefill、decode、生成控制及剩余处理，不是纯 decode。完整 generate 不含模型加载与提前完成的视频预处理。同步 hook 属于剖析设置，不等于未插桩服务延迟。

82 秒前缀的压缩三次耗时为 2.173、1.982、2.235 秒；三次均把输入从 5,056 压到 3,193 个 token。压缩发生在视觉编码之后，本实现没有省去前面的视觉塔计算。

| 前缀 | 输入 token：关 → 开 | 首轮 KV（MiB）：关 → 开 | 整个生成的 footprint 峰值（GiB）：关 → 开 | 压缩阶段 footprint 峰值（GiB） |
|---|---:|---:|---:|---:|
| 4 秒 | 397 → 397 | 13.96 → 13.96 | 8.66 → 8.66 | 7.56 |
| 53 秒 | 3,269 → 2,379 | 114.93 → 83.64 | 10.51 → 9.24 | 8.45 |
| 82 秒 | 5,056 → 3,193 | 177.75 → 112.25 | 11.06 → 9.61 | 8.50 |

footprint 为 macOS `ri_phys_footprint`，峰值采用 10 ms 采样加阶段边界，再对三次峰值取中位数；可能遗漏更短尖峰。它包含模型和运行时，**不是压缩模块独占内存**。RSS、MPS allocator、driver 指标分别保留在 JSON，不相加。实际权重张量为 6.99 GiB；本次新进程模型加载 17.64 秒（文件缓存未清空），加载后 footprint 约 7.30 GiB。MPS 外部映射权重没有完整体现在 allocator 中，不能用其几 KB 计数声称模型几乎不占内存。

对照的完整生成时间逐次列在下面；保留漂移，不删除慢样本或挑最快一次：

| 前缀 | 无压缩，三次秒数 | FluxMem，三次秒数 |
|---|---|---|
| 4 秒 | 2.32, 2.47, 48.47 | 2.29, 8.01, 10.61 |
| 53 秒 | 25.50, 27.02, 77.13 | 27.22, 25.10, 81.55 |
| 82 秒 | 47.77, 92.43, 124.29 | 59.54, 45.95, 108.02 |

系统观察从完成第 16 次调用后才开始，不能解释更早调用的全部波动。三次重复、三道同视频问题，也不足以估计部署中的 P95 或宣称质量等价。

视频读取与 processor 在加载模型前单独进程运行。4 / 53 / 82 秒前缀分别耗时 0.459 / 8.421 / 12.991 秒，采样 RSS 峰值为 0.62 / 2.76 / 3.63 GiB；不能把它们计作零，也不能与另一个进程的峰值直接相加。预处理只测了一轮，不提供误差条。

作者 torchvision 读取器先解码全部前缀再抽帧，82 秒 1080p 原始 RGB 约 12.8 GB。因此仅对解码保留方式做适配，仍使用作者帧数/索引、resize 和 processor。4 秒前缀已与原读取器逐像素及采样率核对；更新到 Torch 2.13 后重新准备三题，所有实际输入张量与旧版本逐元素相同。

实际兼容过程保留为证据：Torch 2.6 在视觉三维 SDPA 失败；2.9 完成短问答，但长期合并的 int64 scatter-reduce 失败；2.13 的短期与长期完整模型路径通过，并在新进程完成正式重复。没有为绕过失败而换掉 FluxMem 的聚类或剪枝算法。

运行版本：Python 3.12、Torch 2.13、torchvision 0.28、Transformers 4.50、PyAV 16.1。模型参数全部在 MPS 上，BF16；short_frames=8、medium_frames=64，1 FPS、最多 96 帧、实际分辨率 224×420，作者已有 video_chunk_t=2；greedy，最多 32 个新 token，所有正式回答实际生成两个 token（选项及结束符）。

作者示例为 7B/CUDA/FlashAttention2；这里是 3B 端侧部署变体，不是论文表格的严格复现。FluxMem 代码 Apache-2.0，3B 官方权重完整公开但限非商业研究，不是无用途限制的开源许可。没有测试摄像头常驻、功耗、手机或独立 writer。
