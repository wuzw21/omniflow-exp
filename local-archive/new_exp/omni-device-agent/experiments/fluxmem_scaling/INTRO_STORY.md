# Intro 与 story：我们到底在做什么

## Intro

端侧持续视觉 agent 的瓶颈不只是第一次看视频，而是视频已经被看过之后，用户不断追问。端侧视觉塔把新到达的画面变成视觉特征；记忆模块再从截至当前的完整前缀中做相邻匹配、剪枝和长期合并。若系统只缓存视觉特征、每次查询都重新运行记忆模块，那么同一段历史会被重复扫描。这个重复计算不会出现在单次问答的 benchmark 中，却会随着查询变密直接进入交互延迟。

我们研究的是这个执行问题，而不是提出新的记忆策略：在固定采样、固定 FluxMem 阈值和固定模型下，把“每次查询重算整个前缀”的 B 与“新块到达时维护一次状态、查询时只读出”的 C2 放在同一条真实 188 秒视频上比较。C2 仍调用原作者的匹配、剪枝和长期合并函数，因此任何输出差异都能归因于状态执行方式，而不是策略改变。我们逐前缀检查保留位置和合并特征，再改变查询间隔，分别测维护时间、完整视觉前端时间和持久 tensor 状态。

这个 setting 暴露出一个部署侧的双重 scaling：B 的计算量由视频历史长度和查询次数共同决定；C2 把策略维护从查询路径移到新增内容路径，但仍需要保存不断增长的长期保留特征，并在每次查询组装读出。问题因此不是“缓存能否复用”，而是端侧 agent 的状态应该在哪个时间轴上被维护，以及这次重排是否真的降低了用户可感知的执行成本。

## Story

1. **先固定真实输入。** 同一条 StreamingBench 足球视频从 82 秒延长到 188 秒，1 fps、两帧一块。94 个前缀全部由真实 Qwen2.5-VL-3B 视觉塔产生；前 41 块与上一轮输入逐元素一致。

2. **先证明 C 没有改变算法。** C2 使用固定短期 ring 保存邻域匹配需要的工作区，剪枝后按帧保存原策略保留的特征，长期合并仍调用原 helper。94 个前缀与原版全量执行逐位一致，188 秒时保留 4258 个 token。

3. **再改变查询密度。** 在同一批视觉特征上，每 40、10、4 秒读出一次，分别得到 6、20、48 次读出。B 每次都重新处理整段历史；C2 只处理新增块并组装当前读出。188 秒维护时间从 B 的 17.45 秒、56.70 秒、104.11 秒增长，而 C2 保持在 5.79 秒、5.69 秒、4.92 秒。这个差异在没有视觉编码噪声的记忆重放中仍存在，所以不是把视觉塔变快了。

4. **把结果放回完整前端。** 真实视觉编码、状态维护和读出组装都计入后，B/C2 总时间分别为 83.45/71.24 秒、114.35/71.83 秒、198.99/82.11 秒。查询越密，B 的重复维护越明显；C2 的总时间增长较慢。每种密度只有一对前端运行，因此这是 scaling 证据，不是稳定性区间。

5. **状态成本没有消失。** B 的特征缓存从 82 秒的 19.22 MiB 增到 188 秒的 44.06 MiB。C2 从 14.45 MiB 增到 19.03 MiB：短期 ring 是固定项，长期保留特征和每次读出需要的组装仍随历史增长。C2 解决的是重复策略执行，不是有界记忆，也不是零成本查询。

6. **因此当前工作的边界很明确。** 我们已有的是一个经过真实模型、真实视频和逐前缀等价性验证的端侧执行适配，以及一条可观测的 scaling 证据链；还没有声称新的记忆质量、完整 agent 任务收益、手机峰值、功耗或任意长视频下的有界状态。下一步如果要继续，必须直接处理 C2 的长期保留状态或读出组装，而不是重新包装“增量”这个名字。
