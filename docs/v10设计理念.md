# OmniTransfer V10：设计理念、实现方法与优势

## 1. 要解决的问题

跨设备 Function 复用包含两个不同问题：

1. 当前页面是否仍然是历史 Function 可以执行的页面。
2. 如果页面匹配成功，历史 action 在当前页面中应该作用于哪个具体 UI 节点。

传统方法通常依赖：

- Resource ID
- XML path
- child index
- source-device 坐标
- 单一截图相似度
- 预先构建的 UTG

这些方法在布局变化、WebView、广告弹窗、列表重排、动态内容和无文本图标场景下都不稳定。

OmniTransfer V10 的核心目标是：

> 用同一套局部化 UI 表示，同时支持页面级匹配和节点级 action 定位。

---

## 2. 总体设计理念

OmniTransfer V10 不是把整页直接压成一个 embedding，也不是为每一种 UI 节点单独训练一个模型。

它使用：

```text
一个共享的多模态节点 Encoder
        ↓
节点级自适应 modality routing
        ↓
学习到的稀疏局部图
        ↓
graph-conditioned element states
        ├── page-level readout
        └── element-level matching
```

其中最重要的设计原则有四个：

### 2.1 表示对象是 Canonical Node

每一个 XML/UI 节点都保留为一个独立的匹配端点。邻居只提供上下文，不会和中心节点合并。

例如：

```text
Alice 的 TextView
Alice 旁边的电话 Icon
联系人 Row
Avatar
```

它们分别有自己的节点表示，但通过局部关系共同帮助定位电话图标。

### 2.2 同一个 Encoder，不同节点产生不同激活

V10 的 Encoder 参数是共享的，但不同节点的输入证据不同，因此 modality router 产生的权重也不同。

例如：

- 文本节点：text 和 XML 权重更高
- 头像节点：visual crop 权重更高，XML 的 widget type 和 geometry 提供辅助
- 电话图标：visual、widget type、geometry 和局部关系共同决定表示
- 没有文字的 WebView 控件：更依赖视觉和局部结构

因此，V10 不是：

```text
Text Encoder + Icon Encoder + Avatar Encoder
```

而是：

```text
Shared Encoder
    + node-specific soft modality routing
```

这使模型可以根据当前节点实际拥有的证据选择信息来源。

---

## 3. 输入：同步的 Screenshot 与 UI Hierarchy

每个 UI observation 包含：

```text
Screenshot
UI hierarchy / accessibility tree
window information
screen and coordinate metadata
```

Screenshot 提供视觉证据：

- 图标外观
- 边缘和形状
- 局部颜色
- 控件是否被遮挡
- WebView 中 XML 无法表达的内容

UI hierarchy 提供结构证据：

- 节点类型和 widget class
- text / content-desc
- clickable / editable / enabled 等状态
- 父子关系和 sibling 顺序
- normalized geometry
- parent-relative layout
- row / column / containment / nearby 等关系

Resource ID、XML path、绝对坐标只作为观察记录保留，不能作为跨设备的最终匹配答案。

---

## 4. 第一阶段：单个 UI 节点的多模态编码

V10 对每一个 UI element 独立执行一次 Encoder。

以“Alice 旁边的电话图标”为例：

```text
一个节点 xi
   ├── text / content-desc
   ├── tight visual crop
   ├── nearby visual crop
   ├── widget type / state
   └── normalized geometry
```

这些证据分别经过对应的投影：

```text
text representation
visual representation
XML representation
        ↓
learned modality router
        ↓
fused base element state ei
```

Router 的计算可以理解为：

```text
每个 modality 产生一个可靠性分数
        ↓
softmax
        ↓
按当前节点自适应加权
```

缺失的 text、visual crop 或 XML 字段通过显式 mask 处理，而不是简单地用零向量表示。

最终得到的是每个节点自己的 base state：

```text
e_text
e_call
e_row
e_avatar
e_search
...
```

V10 的典型配置包括：

- learned token lookup text encoder
- deterministic small-control visual descriptor
- state-aware XML feature projection
- softmax modality router
- shared fused node state

---

## 5. XML 的真正作用

XML 在 V10 中不是简单的文字输入，而是提供两种关键证据。

### 5.1 节点自身证据

XML 可以告诉模型：

```text
这是 TextView、ImageView、IconButton 还是容器
是否 clickable / editable / enabled
是否处于 checked / selected / focused 状态
节点的局部大小和纵横比
节点相对于父节点的位置
```

这些信息帮助模型理解：

```text
“这个东西是什么类型的控件”
“它是否可能是一个可执行目标”
“它在当前局部布局中的角色是什么”
```

### 5.2 节点之间的结构证据

XML hierarchy 还提供：

```text
parent / child
sibling
ancestor / descendant
same row / same column
control → context
list membership
window layer
```

因此，即使电话图标没有 text 或 Resource ID，模型仍然可以知道：

```text
这个图标属于 Alice 所在的 Row
它和 Alice 文本处于同一局部结构
它与 avatar、container 存在稳定关系
```

这也是 XML 在跨设备变化中仍然有价值的原因。

> XML 提供结构和角色证据，但不被当作绝对真值。视觉关系和 XML 关系共同构成 Observation Graph。

---

## 6. 第二阶段：Point-conditioned Sparse Local Graph

单独的节点 embedding 仍然不够。

例如页面上可能有多个完全相同的电话图标。单独看每个 icon 无法知道哪个属于 Alice，哪个属于 Bob。

因此，V10 为每个中心节点学习一个局部稀疏图。

### 6.1 局部候选的构造

模型先构造一个高召回的局部候选范围，候选来自：

- parent / child
- sibling
- ancestor
- same row / same column
- nearby spatial nodes
- normalized relative geometry

这一步只限制局部关系的计算范围，不会把远处节点从最终 correspondence candidates 中删除。

### 6.2 节点自适应选择邻居

每个中心节点根据自身表示和关系特征计算邻居得分：

```text
point compatibility
+ typed relation evidence
− spatial distance penalty
− tree distance penalty
```

不同节点的邻居范围可以不同：

- 文本节点可能重视同一行的控件
- 头像节点可能重视所属 row 和相邻文本
- 电话图标可能重视 Alice 文本、row container 和附近控件

V10 使用 point-conditioned sparse graph 和 entmax，使得边权可以：

```text
保留
削弱
完全置零
选择 NULL
```

因此不是强制每个节点使用固定数量的邻居。

### 6.3 局部消息聚合

局部关系最终用于更新中心节点：

\[
z_i =
\operatorname{Update}
\left(
e_i,\,
\sum_{j\in\mathcal N(i)}
\alpha_{ij}\,
\phi(e_i,e_j,r_{ij})
\right)
\]

其中：

- \(e_i\)：中心节点自身表示
- \(e_j\)：邻居节点表示
- \(r_{ij}\)：节点之间的结构和几何关系
- \(\alpha_{ij}\)：学习到的邻居重要性
- \(z_i\)：graph-conditioned contextual state

V10 重复执行两层局部图更新，使节点获得多跳局部上下文。

计算上使用 padded adjacency list，而不是首先构造完整的 \(N\times N\) 关系张量，因此局部关系成本由近似稠密的 \(O(N^2)\) 降为有界的稀疏局部计算。

## 7. Page-level Readout：页面匹配

Page Matching 的目标不是寻找某个具体电话图标，而是判断两个完整页面是否属于同一个可复用页面状态。

例如：

```text
Page A：一个聊天对话框
Page B：同一个聊天对话框，但聊天记录发生变化
```

两页可能拥有不同：

- 消息文本
- 消息数量
- 时间戳
- 气泡长度

但它们仍然拥有相同的：

- 对话框标题
- 消息列表结构
- 输入框
- 附件按钮
- 发送按钮
- 主要布局

因此，Page Matching 应该保留页面结构，同时降低动态聊天内容的影响。

### 7.1 Token-state matrix

对页面中的 contextual element states 进行堆叠：

\[
Z =
\begin{bmatrix}
z_1\\
z_2\\
\cdots\\
z_N
\end{bmatrix}
\]

其中每一行是一个 graph-conditioned UI node。

### 7.2 Learned slot importance

Page readout 使用多个 learned slots。每个 slot 都对同一批节点计算不同的重要性：

\[
A_{k,i} = \operatorname{Score}_k(z_i)
\]

然后在节点维度上做 softmax：

\[
W_k = \operatorname{softmax}(A_k)
\]

每个 slot 得到一个加权页面摘要：

\[
h_k = \sum_i W_{k,i}z_i
\]

最后：

\[
p = \operatorname{Normalize}
\left(
\operatorname{Concat}(h_1,h_2,\ldots,h_S)
\right)
\]

关键点是：

- slot 不是固定的“文字槽”或“图标槽”
- 每个 slot 都是在同一批节点上学习不同的重要性分布
- 低信息动态聊天记录可以获得较低权重
- 标题、输入框、发送按钮、列表结构等稳定控件可以得到更高权重

两个页面分别得到：

```text
pA = encode(Page A)
pB = encode(Page B)
```

然后使用：

\[
s_{\text{page}} =
\operatorname{CosineSimilarity}(p_A,p_B)
\]

输出 page-match score。

Page Matching 比较的是两个完整 page representations，而不是某个局部 icon。

## 8. Element-level Matching：精确定位 action 目标

Page Matching 成功后，系统还需要定位具体 action 的目标。

例如：

```text
任务：Call Alice
```

Source 页面：

```text
Alice row + Alice 旁边的电话图标
```

Target 页面：

```text
Alice row + call icon
Bob row + call icon
```

Alice 和 Bob 的电话图标视觉上可能几乎相同，因此不能只按 icon appearance 选择。

### 8.1 Source 与 target 的 contextual states

系统分别得到：

```text
zsource =
[Alice text,
 call icon,
 contact row,
 avatar,
 local relations]

ztarget =
[Alice text,
 call icon,
 contact row,
 avatar,
 local relations]
```

Bob 的电话图标则具有：

```text
call icon
+ Bob text
+ Bob row context
```

### 8.2 Element affinity

V10 首先计算 source node 与 target node 的 affinity：

\[
M_{ij}
=
\lambda\,
\operatorname{sim}(z_i^S,z_j^T)
+
\frac{1}{2}
\left(
q_i^S+q_j^T
\right)
\]

其中：

- 第一项表示两个 contextual states 的相似程度
- \(q_i^S,q_j^T\) 表示 source/target node 的 matchability
- 局部关系和 graph prior 会进一步参与匹配

然后通过 source-to-target 与 target-to-source 的双向归一化得到 soft correspondence：

\[
P =
\frac{1}{2}
\left(
\operatorname{softmax}_{row}(M)
+
\operatorname{softmax}_{col}(M)
\right)
\]

系统不是只返回一个目标，而是保留完整候选排序：

```text
Alice-call  → highest score
Bob-call    → lower score
other call  → lower score
```

Alice 的目标被选中，是因为：

```text
Alice 文本一致
call icon 角色一致
所在 row 结构一致
avatar / sibling / nearby 关系一致
```

而 Bob 的电话图标虽然外观相似，但局部邻居是 Bob，因此整体匹配分数较低。

## 9. 最终执行与安全机制

Element Matching 输出的不是“直接点击坐标”，而是：

```text
matched target Canonical Node
+ candidate score
+ matchability
+ uncertainty
```

执行过程是：

```text
source action point
        ↓
source node 内部的归一化位置
        ↓
target matched node 的 bounds
        ↓
投影到 target node 内部
        ↓
执行 action
```

系统绝不：

- 复制 source-device 坐标
- 直接使用 Resource ID
- 直接使用 Node ID
- 直接按 child index 查找
- 选择页面中第一个相似 icon

如果：

```text
最高候选分数不足
matchability 不足
source-to-target 与 target-to-source 不一致
局部上下文不稳定
```

则输出：

```text
Transfer Failure
        ↓
正常 VLM fallback
```

这是 fail-closed 设计：不确定时不执行错误 action。

## 10. V10 相对于旧方法的核心优势

### 10.1 比单一 XML 匹配更稳健

XML 可以处理结构、widget type 和状态，但无法可靠描述：

- 无文本 icon
- WebView 中的视觉控件
- 动态渲染内容
- 同类节点之间的视觉区别

V10 让 XML 与视觉共同参与节点表示。

### 10.2 比单一 screenshot embedding 更精细

整页图像相似度无法回答：

```text
这个电话图标属于 Alice 还是 Bob？
```

V10 将页面拆成节点，并通过局部结构完成 action-level 定位。

### 10.3 比固定邻居或稠密图更高效

V10 不构造所有节点之间的完整关系矩阵，而是：

```text
高召回局部候选
        ↓
point-conditioned edge scoring
        ↓
稀疏边权
        ↓
局部消息更新
```

局部计算是有界的，同时保留所有节点作为最终候选。

### 10.4 比固定模态比例更有适应性

不是固定使用：

```text
50% text + 30% visual + 20% XML
```

而是每个节点根据可用证据自适应选择：

```text
text-heavy node
visual-heavy icon
XML-heavy structural node
```

这使模型能处理字段缺失、文字消失和视觉噪声。

### 10.5 一个表示支持两个任务

Page Matching 和 Element Matching 不使用两套互不相干的 Encoder。

它们共享：

```text
multimodal node states
graph-conditioned contextual states
```

区别只在于输出方式：

```text
page readout → page vector → page matching
element matcher → node affinity → action localization
```

这样可以保证页面检索和 action 定位使用一致的 UI 语义。

### 10.6 对动态内容更合理

对于聊天记录、推荐内容、广告文字等低信息动态内容，Page readout 可以降低其重要性；而对话框骨架、输入区、按钮和列表结构仍然保留较高权重。

因此：

```text
内容变化 ≠ 页面一定变化
```

但如果 action 目标本身发生变化，例如 Alice 不存在，Element Matching 仍然可以拒绝执行，而不是错误地点击 Bob。

## 11. V10 与 V9 的核心区别

V10 保留了 V9 的主要输入思想：

- 多模态节点表示
- state-aware XML
- parent-relative layout
- 双向 candidate matching
- page attention readout

但 V10 将局部关系机制改成了显式的 point-conditioned sparse graph：

| 组件 | V9 | V10 |
|---|---|---|
| 节点表示 | 多模态节点 state | 更宽的多模态 point state |
| 局部关系 | 有界关系列表 | 显式稀疏局部图 |
| 邻居选择 | 固定或排序式选择 | 节点自适应 edge score |
| 边权 | 较固定 | entmax + NULL，支持变量数量邻居 |
| 局部更新 | relation token 更新 | edge-conditioned graph update |
| Page readout | 多个 learned slots | graph-conditioned learned slots |
| 目标 | 局部关系增强匹配 | 局部图直接参与跨页面结构对齐 |

V10 的本质改进不是简单地把 Top-K 换成另一个 Top-K，而是：

> 让每个节点学习“哪些局部关系重要、重要到什么程度，以及是否应该放弃局部关系”。

---

## 12. V10 的边界

V10 并不是无条件地解决所有页面匹配问题。它依赖：

- Screenshot 与 UI hierarchy 的同步
- XML 结构质量
- 视觉 crop 是否有效
- 训练数据是否覆盖真实的布局变化、列表变化和弹窗变化
- confidence threshold 是否经过独立验证集校准

Page Matching 主要判断页面配置是否一致；它不能单独保证某个具体 action 一定可以执行。因此系统必须保留 Element Matching 和 fail-closed fallback。

最终，OmniTransfer V10 的定位可以概括为：

> 一个端侧友好的共享 UI 表示模块：它用节点级多模态编码理解每个 UI element，用 point-conditioned sparse graph 注入局部结构，再分别通过 page readout 和 element matching 完成页面匹配与 action 目标重定位。
